# M18 BW-07 architecture qualification

**Approved for isolated implementation on 2026-11-25.** This design extends ADR-024. The Windows production worker has completed one supervised local capture and isolated restore. Native activation, scheduler changes, production remote transport and deployment changes retain their approval gates. [ADR-024](../decisions/ADR-024-standalone-backup-worker.md) · [Implementation plan](M18_BACKUP_WORKER_IMPLEMENTATION_PLAN_20261124.md) · [Production drill](M18_BW08_QUALIFICATION_20261125.md#supervised-production-baseline)

## Writer coordination

The production capture command completed in **2.085 s**, including archive and receipt publication. It captured 28 files and produced a 390,397-byte archive. One small generation cannot bound downtime. Measure request drain, writer exit, fence acquisition, capture, receipt publication and safe restart separately on representative workloads. The measured capture supports starting with a short coordinated pause and deferring snapshots.

Current enrollment is optional when `LAEW_INSTALLATION_FENCE` is unset. The `ui` CLI and direct Workbench server enroll when configured. The vault reorganization script conditionally enrolls. Direct store access, legacy and maintenance entrypoints, editors, plugins, sync, WSL, containers and remote access need explicit coverage or enforced exclusion. The worker holds an exclusive fence through receipt publication. The lock proves participating leases only. Metadata rechecks detect drift, and SQLite online capture establishes consistency per SQLite database. The session files, both databases, configuration and vault need one shared cut. | Topology | Recommendation and trade-off |
|---|---|
| Existing Windows desktop | **Keep supervised capture.** Confirm and hold a manual maintenance window for the complete roster. Desktop editors, Obsidian/plugins, other processes using the operator SID, and broadly writable runtime roots remain outside an enforceable automatic start gate. A protected worker, a scheduler, and a clean process scan cannot close those paths. A verification-only task could be considered independently under its own approval. |

Have one protected, on-demand controller for the fixed unit set and run the Backup Worker separately as a non-root identity. systemd cgroups provide a process boundary for observing complete service exit. ### Managed fixture contract

1. Bind a protected controller to a fixed inventory of writer units, start routes, source roots, profile and fence identity. Latch a protected restart gate before draining. Require every managed writer to pass the gate and acquire its shared lease before opening a source for write. Prohibit unmanaged writes by OS policy. The controller can stop or start only the reviewed units. It exposes no generic shell or service-control interface.
2. Stop admitting work, drain durable state and observe all original writer processes and children exit. A timeout, unauthorized writer or ambiguous state means skip. Ensure one fixed local lock path whose parent and ancestors prevent replacement. The current lock requires an `O_RDWR` handle even for writers and the worker. Limit that grant to the lock file. Qualify effective database and WAL sidecar access with the actual, distinct non-root worker identity. Fail closed on a missing SHM, unsupported journal or a required source write.
3. Issue an authenticated, single-use control record bound to the installation, writer roster, profile, fence, boot epoch, cut ID, generation ID and short expiry. The worker independently validates it, acquires and holds the existing exclusive lease, and checks authority at the commit boundary. The controller keeps the durable gate closed through archive and receipt publication, including the gap between the final callback and receipt. Test a new writer and a lost or expired proof during that gap. Independent verification can follow publication and must precede any replication or healthy status.
4. On success or a proven terminal abort, resume only the originally running units. On controller loss, worker crash, uncertain receipt, reboot or unknown child state, recover the protected journal and keep the gate closed until terminal state is proven. Never resume based only on expiry or a timer. Orphan archives and incomplete receipts never advance verified health. The worker receives no service-control rights.

### Production status isolation

Keep the optional Workbench status channel off on the current same-SID Windows deployment. The operator can check receipts with the protected CLI. ACL and owner checks permit the expected owner to write, so Core running with the same SID can spoof or replace that owner's report. The channel is advisory and carries no capture, restore or retention authority.

For the Debian fixture, reuse the existing atomic v1 reader/publisher. Use a dedicated worker UID and a separate Core reader UID or group. The protected worker-owned status directory uses setgid group inheritance, with reader traversal/read and no directory replacement rights. Keep configuration, proof, credentials and archive media inaccessible to this reader. For Windows, require a separate publisher or reader SID and verify effective write, delete, owner/DACL and ancestor-replacement denial under the actual Core token before enabling it. A dedicated worker identity may require new owner-private profile/media provisioning because the existing worker checks ownership. Treat that as a separate change. Status may go unknown on stale, missing or invalid data. Design remote status as a separate bounded versioned summary so legacy v1 local health retains its meaning. ## Workbench Backup and Recovery settings

Add one section to the existing Settings dialog. Reuse its labelled controls, forms, alert/status regions, tokens and tests. The ordinary `/api/settings` persistence schema is deliberately narrow and its `settings.json` may be archived by M18. Put backup policy, paths and trust material in a separate operator-owned configuration. Workbench shows draft values, permitted selections and sanitized status. A protected local operator surface explicitly reviews and applies changes. A loopback or same-origin request alone is not authorization to change production policy, network allowlists, paths or credentials. Use a separate bounded contract with same-origin, request validation and stale-revision protection. Workbench has no generic file, command, network, service-control or archive access. ### Validation and lifecycle

- The protected side validates the canonical local absolute folder, fixed volume, owner and effective ACL, source/workspace/vault/fence/status overlap, reparse points or unexpected mounts, and available space. Show the resolved destination to the operator. A write probe, if approved, uses one private uniquely named temporary object. No implicit ACL change or root provisioning.
- **Test connection** submits a bounded request. A trusted operator path approves new network destinations and host pins before the SFTP process runs. A test checks pinned host identity, authentication and configured folder visibility, with connection and total timeouts. A test performs no backup transfer. If write capability is checked, require a separately described scoped probe, since listing alone gives no write guarantee. Report the test result apart from remote backup freshness.
- The authoritative switch lives with protected configuration. `Disabled` blocks new managed capture, replication, retries and connection tests that would resolve credentials. A requested disable takes the admission lock, prevents new work and reports `Disabling` until active work reaches a documented terminal boundary. Finish or cancel in-flight work safely, keeping committed generations and ignoring abandoned partials. Once `Disabled` is effective, no operation can publish a new generation until a separately authorized enable. Drafts and existing archives remain. Verification and separately authorized isolated restore remain available. A legacy direct CLI path cannot bypass the effective master policy for the managed installation.
- Display independent local and remote states. Local shows destination validation, last fully verified generation and a bounded failure reason. Remote shows disabled/unconfigured/invalid or pending/failed/verified replication, last connection-test result and last remotely verified generation. Only receipt-backed verification can advance freshness. A stale, missing or wrong-owner report cannot be treated as healthy. Never pass host details, secret references or raw network errors through the health document.

### SFTP transport proposal

Use a separate opt-in replication command under the trusted worker boundary. Reuse system OpenSSH `sftp` and the platform credential mechanism for the first fixture. Verify the executable path and effective launch identity. Enforce an approved destination allowlist, protected strict host-key pins, no ambient SSH configuration, proxy or shell, no forwarding, restricted argv/path grammar, and time and retry budgets. Require a distinct backup-only key and SFTP-only account restricted server-side to the approved directory and operations. An OS-protected worker-account agent/custody mechanism must be usable under the actual login mode after reboot. Workbench stores and displays a non-secret key label and opaque handle only. Limit the first scope to key authentication. Credential import, password support and rotation/revocation with operational effects need separate decisions. [OpenSSH client configuration](https://man.openbsd.org/ssh_config) · [SFTP batch client](https://man.openbsd.org/sftp) · [Windows OpenSSH key custody](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)

1. Independently verify the committed local ZIP, manifest, members and receipt, and bind the matching release record. Release the writer gate after the local cut completes. Replication never extends downtime and never reads the live sources.
2. Upload the required recovery set under private temporary names. Read back the remote bytes and verify hashes against the committed local set. Publish final immutable names without overwrite and a small verified commit marker last. Remote scanners or restore eligibility require that marker and all its verified dependencies. A connection test, successful upload or existing ZIP alone cannot advance remote health.
3. Test same-filesystem rename, no-clobber and interruption behavior on the selected server. Reject conflicting generations and servers that cannot enforce the publish protocol. Define remote at-rest confidentiality and the server durability guarantee separately. SFTP encryption protects the transfer. Server-side durability and recovery require their own evidence. Remote failure preserves local evidence. Retry only the same verified generation under the protected policy. Delete neither committed remote nor local data through this feature.

## Approval decisions and planned order

1. **Writer topology.** Approve managed Debian fixture qualification with the fixed controller and existing fence. Keep current Windows supervised. Alternative options are to qualify both platforms in isolated managed fixtures, which adds Windows writer-identity and vault work, or defer BW-07 and continue supervised. No production permission or identity changes are requested here.
2. **Workbench authority and status.** Approve Workbench drafts, approved destination selections and sanitized views paired with a protected operator confirmation. Keep production Windows status disabled until independent SID isolation is separately approved. An immediate apply/test broker with explicit operator authentication is possible and adds a security boundary to design and test. Generic Workbench writes to protected policy are outside ADR-024.
3. **Remote fixture.** Approve key-only OS-backed custody, an operator-pinned SFTP endpoint, full readback verification and receipt-last publication, with no activation. Alternatively implement the local-only settings first and hold transport. Approve a specific server, key provisioning, network scope and at-rest policy separately before production use.

Sequence the managed-writer fixture and the Workbench/transport fixtures independently. Neither enables unattended production capture, retention or remote transfer. Record native boundary and failure-injection results in the implementation plan before any BW-08 or deployment decision.
