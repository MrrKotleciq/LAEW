The BW-08 controller holds references to the exact reviewed writer units through graceful exit verification over the local system bus. It still requires an observed zero exit and empty process groups. [systemd unit reference method](https://raw.githubusercontent.com/systemd/systemd/v252/src/core/dbus-manager.c#L2741-L2749)

The next build, `9449220782121658b6d08c92542b3d98e57f39b56b2490e5be248d5281ff1e2e`, passed native writer drain but failed sealing on Debian's Python 3.11.2. Its ZIP implementation added a ZIP64 extra to a forced small member while retaining ordinary size fields. The candidate now writes ordinary headers for small members and requests ZIP64 only when the known staged size requires it. The v1 verifier and receipt format remain unchanged. ## Remaining rollout gates

- A rollback to 0.1.0 is a supervised archive-compatible launcher selection. 0.1.0 does not enforce 0.2.0 managed admission or the disabled marker. Before any future managed deployment, prove that the retired executable and account cannot bypass the managed media boundary. A rollback procedure must close managed admission before switching releases and preserve both release reviews, all receipts and the previous launcher.
- Windows has valid signed system OpenSSH 9.5p2 executables. The host agent is stopped and disabled. The host SSH server is outside the fixture. The managed gate and controller use Debian-specific boot, identity and cgroup behaviour, and the transport explicitly refuses Windows. The host has no Windows Sandbox executable. The read-only elevated Hyper-V census found zero guests. Windows needs a disposable VM and an adapter that proves service descendants have exited, restart stays inhibited, stale or replayed cuts fail and noninteractive worker tokens can use a dedicated agent key with Core denied private access. The current desktop writer scope remains supervised.
- Status is advisory and the publisher must own a protected path. Debian no-write/read-only grants and Windows AppContainer isolation passed their respective fixtures. Windows remains off until the real Core and worker identities and all path ancestors are qualified against replacement. A successful test connection carries no archive or recovery authority.
- An approved production SFTP endpoint, server storage durability, off-host recovery credentials, and unattended timers remain deployment decisions. The isolated loopback server did not qualify any production endpoint.
- Native Debian coverage is for the fixed synthetic service set and the two observed process failures. Validate the real writer roster, distinct operating identities, restart controls and representative cut timing on any proposed Debian deployment before approval. Power loss during publication and the Windows managed lifecycle remain open representative-host tests.

### ChromaDB lifecycle investigation

On Windows, ChromaDB 1.5.9 reproduced the exact reader failure without importing LAEW, using the default embedded cache capacity of 102. Each trial created a fresh temporary `PersistentClient` with two collections, upserted three synthetic two-dimensional vectors in each, and queried A, B, then A. Two of 192 trials failed on the final A query. Both collections still had their three records and four native HNSW files. Neither vector segment had `index_metadata.pickle` or a SQLite sequence-watermark row. The fresh client and store in each trial exclude a preceding LAEW test or LAEW backup lifecycle as a prerequisite for the failure.

The matched control requested a per-collection `sync_threshold` of three, with the same vectors and query order. All 192 trials passed. This supports the unsynchronized-segment reload explanation but does not directly measure cache shard assignments. ChromaDB 1.5.9 falls back from the local cache to disk and refuses an uninitialized persistent segment when its ID-map metadata is unavailable. Issue #7946 describes that path after eviction, including reports with two small collections. The LAEW drill uses the same small, embedded project and global collection pattern. The earlier LAEW failure did not capture cache events, so attribution of that specific event is consistent with the reproduction and remains unproven at the eviction level. [Issue #7946](https://github.com/chroma-core/chroma/issues/7946) · [ChromaDB 1.5.9 local segment manager](https://raw.githubusercontent.com/chroma-core/chroma/1.5.9/rust/segment/src/local_segment_manager.rs) · [ChromaDB 1.5.9 persistent reader](https://raw.githubusercontent.com/chroma-core/chroma/1.5.9/rust/segment/src/local_hnsw.rs)

A second standalone experiment exceeded the default 102-entry cache with 134 small collections. Each passed its initial query. On the next pass, 75 of 134 failed under the default threshold of 1,000. None of those segments had metadata or a watermark. The matched threshold-three control persisted metadata and a watermark for all 134 segments and passed all 134 subsequent queries.

No LAEW code, test assertions, ChromaDB dependency or RAG settings changed for this investigation. The targeted native run passed all nine tests. Qualify a future stable ChromaDB release containing the relevant HNSW changes on the same default-settings reproducer and the unchanged LAEW recovery and full suites before adopting it. The package and production configuration changes require separate approval. [Upstream live-index changes](https://github.com/chroma-core/chroma/pull/7765) · [Upstream idle-file handling](https://github.com/chroma-core/chroma/pull/7869)
