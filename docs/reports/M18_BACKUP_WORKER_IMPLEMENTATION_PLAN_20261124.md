## Verified baseline

The original baseline was the dirty `codex/m18-monitoring-telemetry-backup` checkout at `eff4284`, an editable Core environment, and an empty private Windows backup destination outside the workspace. The read-only plan identified eight logical sources, with named sessions and conversations sharing one physical root. ### Workbench and remote extension

The operator approved the three architecture decisions on 2026-11-25. Workbench, protected policy and Debian SFTP were implemented and exercised in fixtures. Production activation remains outside this approval.

The candidate includes a pinned-unit Debian controller, persistent gate, single-use cut and independent receipt verification before normal resume. Workbench prepares bounded proposals for the protected operator surface, plus a read-only projection. The policy denies new admissions on disable, while an already admitted operation reaches a terminal boundary without deleting archives. The SFTP adapter uses system OpenSSH on a non-root worker with a dedicated agent and approves server capability separately. Native Windows agent and managed-service adapter qualification remain open. [Fixture runbook](../examples/m18/BW07_FIXTURES.md)

| Proposed work | Dependencies and acceptance |
|---|---|
| Backup & Recovery Settings | Approve the UI/operator boundary. Reuse Settings layout, controls and tests. Provide master disable without deletion, local disk/folder selection, exact muted placeholders, useful short help, and independent destination and health states. Keep privileged config outside ordinary Workbench settings. Verify empty fields never save placeholder examples. |
| Protected destination and trust validation | Approve a protected review surface, approved volume/folder catalogue, remote endpoint and key model. Validate ownership, permissions and source separation. Use explicit connection testing with pinned host identity, bounded SFTP and non-secret errors. Verify neither an untrusted UI request nor a saved draft activates execution. |
| SFTP replication fixture | Requires an approved server capability contract and OS-backed key custody. Transfer only independently verified local generations. Prove readback hashes, no overwrite, receipt-last commit, disable/in-flight behaviour, retries and distinct remote health. No local or remote retention. |
| Status boundary qualification | Requires separate reader and publisher identities or equivalent effective OS isolation. Keep the current Windows channel off. Test real worker token, read-only Core token, ancestor replacement denial and lack of private media access. |

The Workbench and transport fixtures do not depend on managed production capture. Their topology, field copy, SSH decisions and failure semantics are in the [architecture proposal](M18_BW07_ARCHITECTURE_QUALIFICATION_20261125.md#workbench-backup-and-recovery-settings).

## Verification matrix

- **Packaging and trust.** Test installed artifacts with no source checkout on the import path, offline, from an unrelated working directory. Verify module origins with Python isolated mode, no editable finder/startup hooks and a tested least-privilege identity. Exercise known bad executable/config ACLs and route a reviewed manifest through the actual path resolver without changing operational storage. Confirm pre/post installation release hashes and validate the prior release after rollback. Test release mismatch and a missing or untrusted provenance record.
- **Canonical compatibility.** Use existing M18 archive, inventory, fence, operator, restore/validation and crash tests plus focused Worker/Core differential fixtures. Assert archived bytes, logical roster and exclusions where deterministic. Compare v1 canonical semantics rather than random IDs and timestamps. Restore disposable named and scoped sessions, project identity, both stores including memory outbox and knowledge publication state, and a committed WAL generation. Check unsupported schemas fail closed. Repeat the Linux root/non-root WAL comparison in fixtures if available. Support non-root Debian and leave pointer to the prior failure rather than weakening the inventory check. Test Windows native ACL and reparse/hardlink behavior with the deployed identity.
- **Cuts and publication.** Simulate missing, restarted and unknown writers, same metadata with different logical state, failed drain, lock replacement, expired or replayed proof, unexpected mount or sidecar, restart before and after ZIP publication, and crash before or after the receipt. Assert no new eligible receipt without a valid cut and verify the prior generation. Test whether a timed-out child can continue after its parent/controller dies and qualify recovery of inhibition state. Test the deliberate race where an external writer attempts to reopen during the cut. A deployment that cannot exclude it is supervised only.
- **Scheduler and status.** Use disabled templates first. Simulate simultaneous, missed, logged-out, rebooted and late/resumed launches on Windows and Debian. Test strict parser fields, future timestamps, ACL spoofing, a stale observation even if previous archive was fresh, and concurrent publication/read failures. Verify bad status cannot authorize backup or alter retention. Track missed RPO from outside the host where needed and treat an old receipt, offline host or failed monitor as distinct observations.
- **Recovery and release.** Recheck archive and receipt independently before restore, restore to a fresh private target, retain a recoverable previous artifact, and exercise version rollback and multiple old receipts. Test no target overwrite and no worker/network startup during isolated recovery. Run any real derived rebuild separately. The existing 24-hour recovery-point and 2-hour canonical recovery figures are fixture targets pending deployment evidence.

## Deferred production choices

1. Qualify an enforceable managed Windows topology in an isolated guest. The approved Debian fixture topology and first Windows supervised window are complete. Further production captures require fresh cut approval and validation. Scheduling remains a separate decision.
2. Qualify the actual Windows status reader and worker identities before enabling the Workbench projection. A production remote endpoint, credential provisioning, and unattended logon/network access need separate qualification and approval.
3. Choose a separately protected off-volume or off-host recovery copy. The first verified local copy still shares the source disk. Platform snapshots remain conditional on pause measurements and a validated coordinated cut.
