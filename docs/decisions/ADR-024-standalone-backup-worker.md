# ADR-024 — Standalone LAEW Backup Worker

## Status

Accepted. The operator approved BW-01–BW-06 and supervised-first delivery. Production installation, capture, identity changes, scheduler activation and retention each retain their existing authorization gates. [M18 implementation plan](../reports/M18_BACKUP_WORKER_IMPLEMENTATION_PLAN_20261124.md)

The first supervised Windows production capture and isolated restore are complete. The operator approved the BW-07 topology, Workbench settings and remote replication for isolated implementation. Unattended Windows remains a target. [Production drill](../reports/M18_BW08_QUALIFICATION_20261125.md#supervised-production-baseline) · [BW-07 architecture qualification](../reports/M18_BW07_ARCHITECTURE_QUALIFICATION_20261125.md)

## Context

When this decision was drafted, the M18 engine could capture, verify and restore a single-host archive with a declared writer cut. A private production destination and profile had passed read-only planning and listing. The Windows editable venv loaded modules from the broadly writable workspace even with Python isolated mode. The installation fence had no verified production writer enrollment and the archive destination was empty. [Production readiness evidence](../reports/M18_BW08_QUALIFICATION_20261125.md#supervised-production-baseline)

The runtime cut is achievable because archive verification, fencing and ZIP I/O are already standalone. Current inventory and recovery import through Console, RAG, memory and knowledge packages, pulling application modules, Requests and NumPy into backup processes. PyYAML is needed for the existing manifest. Keep its validation and use the standard library for SQLite, paths, hashes, archives, locks and JSON. [Dependency evidence and scope](../reports/M18_BACKUP_WORKER_IMPLEMENTATION_PLAN_20261124.md)

## Architectures considered

| Option | Benefits | Costs and limits |
|---|---|---|
| **A. Minimal worker wheel built from the shared repository** | Reuses the M18 engine, supports both platforms and isolates the installed execution chain. Independent of the Core process and full dependency set. | Requires import boundaries, a release allowlist, compatibility tests and a protected worker environment. Shared Python namespace requires separate environments. |
| B. Shared library under a distinct package name, consumed by Core and Worker | Clear package ownership and safe co-installation. Good option if other consumers emerge. | Higher migration cost for stores, validators and existing imports, and coupled version selection across two distributions. |
| C. Run the existing full distribution in a protected environment | Smallest change to code and existing receipt provenance. | Installs a second full LAEW distribution and retains the current dependency and update surface. |
| D. Freeze a backup-only executable per platform, reusing the same engine | Simplifies launching where managed Python is unavailable. | Still needs import separation. Adds platform builds, binary and bundled dependency servicing, and artifact identity/rollback work. Does not solve writer consistency. |

## Proposed decision

Adopt **A**, a separate `laew-backup-worker` distribution and entry point built from the same reviewed source. Ship an explicit allowlist of modules needed for backup and isolated recovery. Install the wheel non-editably in a dedicated environment. Avoid installing it into a Core environment because both artifacts may contain modules in the `laew` namespace. Keep stdlib plus pinned PyYAML as the runtime dependency target and require an end-to-end clean-environment test before declaring that target met.

1. **Shared M18 engine.** Keep one implementation of inventory, capture, archive verification, recovery, exclusions, filesystem safety and fencing. Extract neutral storage path, schema, legacy session validation and project identity helpers where required. Maintain Core's existing imports through delegations and test compatibility. Point the existing operator commands and the worker entry point at the same backup-specific command handlers. The worker exposes plan, list, verify, manual create, and restore verify-only or explicitly approved isolated apply. Automated capture is a separate gated command or mode. Telemetry, Workbench, model calls, retention apply and RAG rebuild stay outside the worker process. Restore checks canonical data offline; any derived index rebuild is a separate Core operation against an isolated copy.
2. **Protected execution.** Run with an absolute trusted Python and protected working directory, using isolated import mode and a non-editable install. Verify the interpreter, dependencies, module origins, startup hooks, executable parent paths, manifests, wrapper and scheduler action. Keep artifacts, profile and captured data outside workspace-writable paths. Bind source resolution to the exact approved manifest and profile bytes. A protected manifest copy is acceptable only after proving equivalent absolute source paths and project identities. Relative session paths depend on both manifest placement and launch cwd. Revalidate the resulting source roster and continue to record the authored manifest digest. The worker reads source files and writes only private staging, archive, status and operator-approved isolated restore paths. Its fence handle must open the existing lock with the correct rights but grant no ability to replace it. Qualify a least-privilege identity distinct from Core for unattended use, or demonstrate an equivalent OS enforcement boundary. Keep administrative writer controls outside the worker's identity.
3. **Release and recovery compatibility.** Preserve archive layout, manifest and receipt schemas, canonical membership, exclusion rules, UUIDs, memory namespace and restore policy. `package_python_sha256` continues to fingerprint the actual executing capture package tree. For a worker archive that is the worker tree. Keep a protected release record that binds the worker artifact hash and package-tree digest to supported Core versions/schemas. Record the independently established source Core release separately, with generation and archive digest for correlation. Provision the release record and manifest separately from the backup; legacy readers can still verify the archive. Never use the worker hash to claim a specific source Core build. Recover older generations with their matching release information. If mixed readers cannot safely recover from these v1 archives, stop release and seek approval for a versioned provenance change. Format compatibility does not imply support for an unknown newer schema.
4. **Updates and rollback.** Build release wheels once from reviewed source and use a pinned, hash-verified offline dependency set. Install each release in a new protected versioned directory and run provenance, plan and fixture verify/restore checks there before switching the approved launcher. Quiesce capture and switch the launcher through the owner-approved mechanism. Retain the previous worker, manifest and release records. Rollback changes that launcher and configuration only, leaving archives and receipts in place. Preserve an independently verified off-volume or off-host copy with the required confidentiality. The current same-disk destination is a staging/first-copy option with no protection against disk loss.

## Multi-source consistency

SQLite's Online Backup API can produce a consistent copy of **one** database, including committed WAL state when opened in the supported manner. Capturing the memory and curation databases separately while vault files or sessions change can yield a generation that never existed as a recoverable application state. Timestamp rescans and referential checks detect some failures and remain defense in depth. They cannot establish a transaction spanning SQLite, JSON and vault/config files. [SQLite Online Backup API](https://www.sqlite.org/backup.html)

Qualify the deployed worker identity against actual read-only SQLite and sidecar access on each platform. If the supported capture path cannot read under that model, stop and report the gap. A future staged-WAL path would require its own common-cut and restore tests. It must not silently grant source-write access, checkpoint an operational store, or copy a live database file without its committed WAL.

| Capture strategy | When acceptable | Trade-off |
|---|---|---|
| **Operator-supervised maintenance window and existing fence** | First production use after approval, actual complete writer inventory, drain, suspension of restart and a current generation-bound acknowledgement. | Portable and uses currently qualified primitives. Requires operator presence and downtime. |
| **Managed maintenance window and cooperative fence** | Unattended only after the installation can prove and enforce the cut for every writer and source, including external writers. | Portable default for unattended use. Adds controlled launch/drain, restart inhibition and recovery from coordinator or worker failure. A free lock proves absence of participating leases only. |
| Coordinated platform snapshots | Future option for shorter pauses when measured need warrants it. Requires a complete quiescent writer cut or a validated application-consistent provider, complete source-volume coverage and stable read-only snapshot views. | Higher privilege, platform-specific tooling and mount/profile work. Windows VSS without participating writers provides a crash-consistent view. Debian filesystem freeze flushes/freezes filesystem activity, which can still preserve an incomplete cross-source application operation. Sequential per-volume snapshots of active sources have no common cut. [VSS writer guarantees](https://learn.microsoft.com/en-us/windows/win32/vss/writers) · [Linux filesystem freeze](https://man7.org/linux/man-pages/man8/fsfreeze.8.html) |

### Unattended protocol

- The operator approves an inventory of writers **and launch/restart paths** bound to the reviewed profile, source paths, file identities where applicable, and fence. Cover Workbench and background workers, legacy/CLI paths, curation publication, migration/maintenance, Obsidian and plugins, editors, file sync and any other principal allowed to write. Establish an enforceable rule for unmanaged writer identities. Optional enrollment and names from a process scan cannot establish coverage. Keep persistent-desktop configurations in supervised mode when an interactive user or background agent can still write or restart outside the managed barrier.
- A separately trusted maintenance controller inhibits cooperating and external launches, drains writes to recoverable application boundaries, verifies shutdown or quiescence and excludes new writes using the proven enforcement boundary. The worker takes the exclusive lease on the same stable fence. Launches must take their shared lease before write access and fail closed when required enrollment is missing. Allow read-only operations during a cut only after their actual permission and behavior are verified. Administrative control must target named, audited units or tasks. Avoid broad process-kill and shell execution interfaces.
- Bind a short-lived, single-use proof to the exact controller/installation/profile digest, approved roster, boot/session epoch, cut and backup UUIDs. Validate provenance through a protected local channel and controller-held barrier; the automatic worker cannot self-assert operator flags. Use UTC expiry plus a monotonic deadline. A protected owner-held journal records proof consumption, process completion and restart state. A stale token, unknown owner, late trigger, blocked fence, configuration drift, unconfirmed external writer or insufficient time produces a skip or failure with a reason.
- Hold the enforced barrier and exclusive fence through archive and **receipt** publication. Add worker engine checks at the commit boundary and test the existing gap between the archive callback and receipt publication. An expiring claim or heartbeat is diagnostic; it cannot replace an enforced barrier spanning publication. Verify the committed archive independently before advancing healthy status. Keep any orphan generation outside the eligible set. A controller recovering from failure must first prove the old operation is terminal or keep writers inhibited and signal operator recovery. Resume only the recorded originally running set. Never restart suspended writers blindly on a timer or infer success from a process exit alone.
- On Windows use Task Scheduler to trigger a least-privilege one-shot worker with `IgnoreNew`, no catch-up or automatic retry, and a time-bounded admission check. Establish whether the batch identity can access the exact local protected paths before enabling a logged-out task. On Debian use a dedicated non-root `Type=oneshot` service and timer with `Persistent=false`, no wake or restart. A resumed calendar event can still arrive late after suspend, so the worker checks the approved live window rather than trusting the scheduler. Do not introduce mount aliases that violate the current capture engine's mount checks. Qualify any sandboxing together with path and WAL access. Keep both integrations disabled until verified on fixture hosts and explicitly approved. [Task Scheduler settings](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings) · [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)

### Threat model and health interface

The relevant risks are hostile workspace instructions or code, unintended access by other local principals, compromised Core or user tooling, malicious archives and tampered configuration. The worker trusts the operator identity, enabled controller, protected release and OS. Host administrator or root compromise can defeat local ACLs. Preserve the meaningful guarantees already used by M18: path/link/mount confinement, hardlink and bounds checks, protected owner paths, no-replace publication, schema and hash validation, original data preservation, audited recovery and no privileged parser over untrusted input. SHA-256 provides integrity relative to a trusted receipt; it cannot authenticate media that an attacker can rewrite together with its receipt. Do not require a model, API, daemon, cloud account, or telemetry pipeline for backup.

Publish a bounded status JSON document in a dedicated local directory with worker write and Core read-only grants. Core gets no access to the private archive, configuration, acknowledgement or executable through this interface. Control the entire status path, including replacement rights. Serialize publication per profile so a concurrent verification cannot overwrite a newer result with stale state. Write a temporary file beside the final file under the approved ACL, flush and verify it, then atomically replace the old file. Use same-volume publication and platform-appropriate durability checks and verify Windows sharing behavior. If publication fails, the older document ages out. Parse a strict, size-limited v1 document without following links. An unexpected identity, malformed timestamp, future time, unsupported schema, missing file or stale observation produces unknown or degraded health. Core must never treat the file as a writer lease or authorization.

| v1 field | Proposed contract |
|---|---|
| `schema_version`, `profile_id` | Schema `1` and expected bounded logical profile identifier. No paths or account names. |
| `observed_at_utc` | Time the worker last wrote a valid report. Use a separately configured observation age for missed runs. |
| `last_attempt` | Operation `capture` or `verify`, UTC completion time, outcome `verified`, `skipped` or `failed`, and an allowlisted machine reason. |
| `last_verified_at_utc` | Original committed generation's verification timestamp or null before the first independently verified archive. Rechecking it later never advances the generation's freshness. |

Keep operation outcome and last verified generation separate. A failed or skipped new attempt can coexist with a previous still-fresh generation. Label expired and corrupt evidence accordingly rather than reporting healthy based on a cached receipt. Only a full matching archive verification advances the verified generation, and a verification failure for that generation removes its currently healthy status until reverified. The existing CLI status JSON remains compatible. Map the opt-in worker report to the existing backup component and retain current operator-only legacy reads during migration. Use coarse reasons in Core, such as `writer_busy`, `cut_unconfirmed`, `archive_verification_failed`, `status_stale` and `no_verified_generation`. Private operator diagnostics can retain narrowly scoped IDs. No paths, payloads, secrets, raw exceptions or archive contents appear in the Core document.

## Release gates

The approved first release is the shared-source minimal worker with supervised capture and opt-in read-only health. Managed writer barriers and unattended pilots require separate approval and proof for each deployment. Choose the Windows and Debian writer-management topology before any pilot. Platform snapshots remain a later decision if the measured maintenance window is unacceptable.
